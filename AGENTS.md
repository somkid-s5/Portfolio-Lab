# Portfolio-Lab working agreement

Read PLAN.md, GCP/ROADMAP.md and GCP/PROGRESS.md before implementation. Source of truth is this GitHub repository. Work in cloud-hosted tools; do not rely on the user's laptop being awake.

User-approved direction:
- 20 GCP solution labs. Each lab is one self-contained story: build, deploy, test, operate, troubleshoot, change request, evidence, cleanup.
- Plan globally, then deepen one lab at a time. Finish the current lab to Guide-ready before the next. Requirements and design precede Task authoring.
- One Thai README per lab contains the learning guide, recording sections and case-study summary. Separate only actual code/scripts/infra/assets.
- Provide working sample applications, schemas, seed data, health endpoints, logs and bounded test tools as needed. Do not reduce the task to create-VM/create-VPC exercises.
- Write natural Thai. Explain where to click/run, exact inputs, expected results, failure diagnosis and next checkpoints. Place recording fields beside the work.
- Keep lab-facing content about the solution. Avoid conversation history or explanations about separation from Personal Knowledge Base/future websites.
- test/lab-test-2/README.md is the approved reading reference, not a completed production lab or real GCP test result.
- docs/diagram-style.md records the approved diagram conventions. Use verified official service icons and preserve attribution. Prefer vertical backends for short fan-out where it fits; choose layout from relationships.
- Never fabricate cloud PASS, performance claims or Console screenshots. Distinguish Guide-ready from Cloud-verified.
- Commit checkpoints to task branches and create/update a PR for review. Preserve existing work, do not force-push or merge without a user request.
- No paid cloud provisioning or website deployment is authorized by the documentation goal.
